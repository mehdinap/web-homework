# پاسخ تمرین‌های Git

## ۱. سؤال اول: بررسی merge و rebase

هر دو دستور برای ترکیب تغییرات دو شاخه استفاده می‌شوند، اما تاریخچه را به شکل متفاوتی نگه می‌دارند.

`git merge` تغییرات یک شاخه را با شاخه فعلی ترکیب می‌کند. اگر شاخه‌ها از هم جدا شده باشند، معمولا یک merge commit ساخته می‌شود که به هر دو شاخه اشاره دارد. در نتیجه تاریخچه نشان می‌دهد کار از کجا منشعب شده و کجا دوباره به هم رسیده است.

`git rebase` کامیت‌های شاخه فعلی را روی آخرین کامیت شاخه مقصد دوباره اعمال می‌کند. این کار تاریخچه را خطی‌تر نشان می‌دهد، اما کامیت‌های تازه با شناسه‌های جدید می‌سازد.

برای مثال، وقتی یک شاخه آماده شده و قرار است وارد `main` شود، می‌توان از `merge` استفاده کرد. این روش تاریخچه شاخه را حفظ می‌کند و مشخص می‌ماند تغییرات در چه مسیری ایجاد شده‌اند.

`rebase` بیشتر برای به‌روز کردن شاخه شخصی با آخرین تغییرات `main` مناسب است. مثلا پیش از ارسال Pull Request می‌توان تغییرات جدید `main` را روی شاخه خود آورد تا تاریخچه مرتب‌تر باشد. بهتر است شاخه‌های مشترک را rebase نکنیم، چون شناسه کامیت‌ها عوض می‌شود و ممکن است کار بقیه اعضای تیم به مشکل بخورد.

## ۲. سؤال دوم: انتخاب بخشی از تغییرات

در خروجی `diff`، هر بخش پیوسته از تغییرات یک فایل را یک **hunk** می‌گویند. در هر hunk خطوط اضافه‌شده، حذف‌شده و چند خط از متن اطراف تغییر دیده می‌شود تا مشخص باشد تغییر در کدام قسمت فایل اتفاق افتاده است.

برای دیدن تغییرات به شکل تعاملی و انتخاب اینکه کدام بخش وارد staging شود، از این دستور استفاده می‌کنیم:

</div>

```bash
git add -p
```

<div align="right" dir="rtl">

برای یک فایل مشخص هم می‌توان نوشت:

</div>

```bash
git add -p path/to/file
```

<div align="right" dir="rtl">

گیت هر hunk را جداگانه نشان می‌دهد. برای انتخاب، یکی از این گزینه‌ها را وارد می‌کنیم:

<div dir="rtl" align="right">
<p>برای وارد کردن آن بخش به staging، کلید <bdi dir="ltr">y</bdi> را می‌زنیم.</p>
<p>برای رد کردن آن بخش، کلید <bdi dir="ltr">n</bdi> را می‌زنیم.</p>
<p>برای تقسیم کردن یک بخش بزرگ‌تر به بخش‌های کوچک‌تر، کلید <bdi dir="ltr">s</bdi> را می‌زنیم.</p>
<p>برای ویرایش دستی بخش، کلید <bdi dir="ltr">e</bdi> را می‌زنیم.</p>
<p>برای خروج از دستور، کلید <bdi dir="ltr">q</bdi> را می‌زنیم.</p>
</div>

این کار کمک می‌کند تغییرات نامرتبط را در یک کامیت نگذاریم. مثلا اگر هم‌زمان یک باگ را رفع کرده‌ایم و قابلیت دیگری هم نوشته‌ایم، می‌توانیم هر کدام را جداگانه کامیت کنیم. در این صورت بررسی تاریخچه و برگرداندن یک تغییر هم ساده‌تر می‌شود.

## ۳. سؤال سوم: پیدا کردن منشأ خطا با git bisect

`git bisect` با جست‌وجوی دودویی بین کامیت‌ها، کامیتی را پیدا می‌کند که احتمالا خطا را وارد کرده است. به جای بررسی تک‌تک کامیت‌ها، گیت هر بار یک کامیت از وسط بازه را برای بررسی انتخاب می‌کند و با توجه به نتیجه، بازه را کوچک‌تر می‌کند.

ابتدا جست‌وجو را شروع می‌کنیم و کامیت فعلی را به عنوان خراب مشخص می‌کنیم:

</div>

```bash
git bisect start
git bisect bad
```

<div align="right" dir="rtl">

بعد یک کامیت قدیمی را که مطمئنیم سالم بوده معرفی می‌کنیم:

</div>

```bash
git bisect good <commit-hash>
```

<div align="right" dir="rtl">

گیت به یک کامیت میانی می‌رود. آن نسخه را بررسی می‌کنیم و نتیجه را اعلام می‌کنیم. اگر خطا در آن وجود داشت:

</div>

```bash
git bisect bad
```

<div align="right" dir="rtl">

اگر سالم بود:

</div>

```bash
git bisect good
```

<div align="right" dir="rtl">

این کار را ادامه می‌دهیم تا گیت کامیتی را پیدا کند که خطا از آن به بعد دیده می‌شود. در پایان، با دستور زیر از حالت bisect خارج می‌شویم و به شاخه قبلی برمی‌گردیم:

</div>

```bash
git bisect reset
```

<div align="right" dir="rtl">

مثلا اگر بعد از چند هفته متوجه شویم برنامه دچار خطا شده، می‌توانیم یک نسخه قدیمی و سالم را با نسخه فعلی مقایسه کنیم تا کامیت مشکل‌ساز پیدا شود. این روش وقتی تعداد کامیت‌ها زیاد است از بررسی تک‌تک آن‌ها سریع‌تر است. اگر تست خودکار داشته باشیم، می‌توانیم بخشی از بررسی را هم خودکار کنیم.

## ۴. سؤال چهارم: بررسی تغییرات پیش از کامیت

### ۱. بررسی وضعیت و تغییرات

برای دیدن وضعیت کلی مخزن از این دستور استفاده می‌کنیم:

</div>

```bash
git status
```

<div align="right" dir="rtl">

این دستور فایل‌های آماده کامیت، تغییرات واردنشده به staging و فایل‌های untracked را نشان می‌دهد.

برای دیدن تغییراتی که هنوز وارد staging نشده‌اند، از این دستور استفاده می‌کنیم:

</div>

```bash
git diff
```

<div align="right" dir="rtl">

این دستور تفاوت فایل‌های working tree با staging area را نشان می‌دهد.

برای دیدن تغییراتی که وارد staging شده‌اند و آماده کامیت هستند، از این دستور استفاده می‌کنیم:

</div>

```bash
git diff --staged
```

<div align="right" dir="rtl">

این دستور تغییرات staging area را با آخرین کامیت مقایسه می‌کند.

### ۲. کامیت بدون گزینه `-a`

اگر در وضعیت گفته‌شده دستور زیر را اجرا کنیم:

</div>

```bash
git commit -m "Update README"
```

<div align="right" dir="rtl">

فقط تغییراتی وارد کامیت می‌شوند که قبلا وارد staging شده‌اند. ویرایش دومی که بعد از آن انجام داده‌ایم و stage نشده، در working tree باقی می‌ماند.

دلیلش این است که گیت هنگام ساخت کامیت، اطلاعات را از staging area می‌گیرد. بنابراین هر تغییری که بعد از آخرین بار `git add` انجام شده باشد، تا وقتی دوباره stage نشود وارد کامیت نمی‌شود.

### ۳. نادیده گرفتن پوشه /tmp

برای نادیده گرفتن این پوشه، الگوی آن را در فایل `.gitignore` در ریشه مخزن می‌نویسیم:

</div>

```text
/tmp/
```

<div align="right" dir="rtl">

این قانون برای فایل‌هایی اثر دارد که هنوز tracked نشده‌اند. اگر فایلی قبلا tracked شده باشد، اضافه کردنش به `.gitignore` باعث نمی‌شود گیت دیگر آن را دنبال نکند. برای خارج کردن آن از رهگیری گیت، بدون حذف فایل از روی دیسک، از این دستور استفاده می‌کنیم:

</div>

```bash
git rm --cached <file-path>
```

<div align="right" dir="rtl">

## ۵. سؤال پنجم: رفع merge conflict در کار گروهی

### ۱. دلیل رخ دادن conflict

در این مثال، هر دو نفر یک خط از `README.md` را نسبت به کامیت مشترک تغییر داده‌اند. چون گیت نمی‌تواند تشخیص دهد کدام نسخه باید بماند، conflict ایجاد می‌شود.

البته هر تغییر هم‌زمانی باعث conflict نمی‌شود. اگر دو نفر قسمت‌های جدا از یک فایل یا فایل‌های متفاوت را تغییر داده باشند، گیت معمولا می‌تواند تغییرات را خودش ترکیب کند.

### ۲. پیدا کردن فایل و متن‌های دچار conflict

با دستور زیر وضعیت مخزن را بررسی می‌کنیم:

</div>

```bash
git status
```

<div align="right" dir="rtl">

فایل‌های دارای conflict زیر بخشی با عنوان `Unmerged paths` نمایش داده می‌شوند. اگر فایل را باز کنیم، گیت دو نسخه را با نشانگرهایی مثل این مشخص کرده است:

</div>

```text
<<<<<<< HEAD
متن شاخه فعلی
=======
متن شاخه دیگر
>>>>>>> feature-description
```

<div align="right" dir="rtl">

خط اول بخش مربوط به شاخه فعلی را نشان می‌دهد، خط `=======` دو نسخه را از هم جدا می‌کند و خط آخر بخش مربوط به شاخه‌ای را نشان می‌دهد که در حال merge شدن است.

### ۳. رفع conflict و تکمیل merge

فایل `README.md` را باز می‌کنیم و متن نهایی را طوری ویرایش می‌کنیم که اطلاعات هر دو تغییر حفظ شود. بعد باید همه نشانگرها را پاک کنیم و بررسی کنیم که در متن نهایی باقی نمانده باشند. برای جست‌وجوی نشانگرها می‌توانیم از این دستور استفاده کنیم:

</div>

```bash
grep -nE '^(<<<<<<<|=======|>>>>>>>)' README.md
```

<div align="right" dir="rtl">

اگر دستوری خروجی نداد، این نشانگرها در فایل پیدا نشده‌اند. سپس فایل را وارد staging می‌کنیم و merge را با کامیت تمام می‌کنیم:

</div>

```bash
git add README.md
git commit
```

<div align="right" dir="rtl">

### ۴. لغو merge

اگر بخواهیم merge در حال انجام را لغو کنیم و به وضعیت قبل از شروع آن برگردیم، از این دستور استفاده می‌کنیم:

</div>

```bash
git merge --abort
```

<div align="right" dir="rtl">

## ۶. سؤال ششم: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱. کنار گذاشتن تغییرات unstaged در notes.txt

برای دور انداختن تغییرات واردنشده به staging در این فایل، اجرا می‌کنیم:

</div>

```bash
git restore notes.txt
```

<div align="right" dir="rtl">

این دستور فایل را به نسخه موجود در staging برمی‌گرداند. در این سناریو، staging با آخرین کامیت یکسان است، پس فایل به همان نسخه آخرین کامیت برمی‌گردد. تغییرات بقیه فایل‌ها و تاریخچه کامیت‌ها دست‌نخورده می‌مانند.

### ۲. خارج کردن notes.txt از staging

برای خارج کردن تغییرات فایل از staging و نگه داشتن ویرایش‌ها در working tree، اجرا می‌کنیم:

</div>

```bash
git restore --staged notes.txt
```

<div align="right" dir="rtl">

این دستور نسخه staging را به آخرین کامیت برمی‌گرداند، اما نسخه فایل در working tree را تغییر نمی‌دهد. بنابراین ویرایش‌ها حفظ می‌شوند ولی دیگر آماده کامیت نیستند.

### ۳. برگرداندن کامیت push‌شده روی main

برای خنثی کردن اثر یک کامیت معمولی که روی شاخه مشترک `main` فرستاده شده، از `git revert` استفاده می‌کنیم:

</div>

```bash
git revert <commit-hash>
```

<div align="right" dir="rtl">

این دستور کامیت قبلی را از تاریخچه حذف نمی‌کند، بلکه کامیت تازه‌ای می‌سازد که تغییرات آن را برمی‌گرداند.

در این شرایط استفاده از `reset --hard` و `push --force` مناسب نیست، چون تاریخچه شاخه مشترک را بازنویسی می‌کند. همکاران ممکن است آن کامیت را در مخزن خود داشته باشند و بعد از تغییر تاریخچه با مشکل هماهنگ کردن شاخه‌هایشان روبه‌رو شوند. `revert` راه امن‌تری است، چون تاریخچه قبلی حفظ می‌شود و دلیل برگشت تغییر هم مشخص می‌ماند.

## یادداشت شفاف‌سازی استفاده از هوش مصنوعی

برای تکمیل و نگارش پاسخ‌های این تمرین، از هوش مصنوعی استفاده کرده‌ام.

همچنین برخی مباحث برای من تازه بود یا رویه متفاوتی در تجربه عملی داشتم که با مطالعه و گفتگو با AI بررسی شد:

- **سؤال ۳ (git bisect):** موضوع برایم تازه بود و از طریق مطالعه و گفتگو با AI مفاهیم و روند آن را بررسی کردم.
- **سؤال ۵ (بخش‌های ۲، ۳ و ۴ - نشانگرهای conflict و رفع آن از طریق command line):** پیش از این تجربه حل conflict را عمدتا با merge کردن شاخه هدف در شاخه خودم، حل conflit در GitLab UI و ساخت Merge Request انجام می‌دادم. نحوه کار مستقیم با نشانگرهای conflict و دستورات ترمینال را با راهنمایی AI مرور و مستند کردم.
